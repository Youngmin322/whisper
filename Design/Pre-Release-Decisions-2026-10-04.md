# Whisper 배포 전 수정의 판단 근거와 대안

2026-10-04. 앱 구현 기준은 `da68d20`이며, 각 수정은 아래에 적은 로컬 커밋에 포함되어 있습니다. 수정 전 관찰은 [프로젝트 검토](Project-Review-2026-10-04.md), 실행 결과와 배포 담당자의 남은 확인 항목은 [배포 준비 기록](Release-Readiness-2026-10-04.md)을 참고합니다.

이 문서는 각 작업을 배포 전에 해야 한다고 판단한 이유와 구현 선택의 근거를 설명합니다. 아래 선택지들은 현재 요구사항에 맞춰 비교한 설계 대안입니다. 모든 대안을 구현하거나 성능을 측정해 비교했다는 뜻은 아닙니다. 검증 항목에는 실제 실행한 내용만 적었습니다.

## 우선순위를 정한 기준

Whisper의 핵심 흐름은 **순간 작성 → 저장 → 수정 → 하루 일기로 모으기 → 다시 읽기**입니다. 이 흐름에서 작성 내용과 사진을 보존하고, 사용자가 저장을 끝낼 수 있어야 합니다. 기존 [경험 설계](Whisper-UX-Decisions.md)의 하루에 하나의 병, 원문 보존, 부담 없는 기록 방향도 판단 기준으로 삼았습니다.

| 기준 | 이번 작업에 적용한 판단 |
|---|---|
| 작성 내용과 사진 보호 | 원본 삭제·수정이 다른 기록이나 작성 중인 초안을 손상시키지 않아야 함 |
| 사용 흐름의 완결성 | 초안이 남아 있어도 완성본으로 저장할 수 없다면 복구 경로가 필요함 |
| 배포 결과의 재현성 | 개인 컴퓨터의 추가 폴더 없이 커밋된 파일만으로 빌드·테스트할 수 있어야 함 |
| 주요 조작의 가독성 | 작성·저장에 쓰이는 작은 글자는 배경과 충분히 구분되어야 함 |
| 변경 범위와 검증 가능성 | 배포 직전에는 기존 저장 구조와 제품 정책을 활용해 수정하고, 실패·재시작 경로를 확인함 |

#32는 이전 버전의 일부 데이터에서 발생하는 조건부 문제이고, #34와 #36은 최초 검토에서 중간 우선순위였습니다. 그래도 기존 기록 보호와 매번 사용하는 작성 흐름에 직접 관련되고 수정 범위를 제한할 수 있어 배포 전 범위에 포함했습니다. 사용성 제안 전체를 배포 차단 사유로 삼지는 않았습니다.

## #31 — 원본이 삭제된 일기 수정 초안 복구

이슈: [#31](https://github.com/Youngmin322/whisper/issues/31) · 구현 커밋: `06c7de9`

### 왜 필요했는가

수정하던 일기를 닫아 초안을 보관한 뒤 원본 일기를 삭제하면, 초안에는 삭제된 원본의 ID가 계속 남았습니다. 홈에서 초안을 재개해도 저장은 없는 원본을 수정하려다 거절되었습니다. 잠시 후 다시 시도하라는 안내로는 해결되지 않았습니다.

초안의 글이 즉시 사라지는 문제는 아니지만, 사용자가 작성한 내용을 일기로 완성할 수 없는 확정된 흐름 오류였습니다. 삭제 자체는 사용자의 의도이므로 원본을 몰래 되살리거나 다른 일기를 덮어쓰는 것도 적절하지 않았습니다.

### 선택지와 판단

| 선택지 | 장점 | 이번에 선택하지 않은 이유 |
|---|---|---|
| 원본 삭제 시 수정 초안도 삭제 | 고아 초안이 생기지 않음 | 완성본 삭제와 작성 중인 내용 삭제를 같은 행동으로 묶어 내용 손실을 일으킴 |
| 수정 초안이 있으면 원본 삭제 금지 | 새로운 고아 초안을 예방함 | 삭제 의도를 제한하고, 이미 남아 있는 고아 초안을 복구하지 못함 |
| 원래 날짜의 일기를 자동 생성하거나 기존 일기에 합치기 | 추가 선택 없이 저장 가능 | 같은 날짜에 다른 일기가 있으면 덮어쓰기·중복 문장·사진 배치의 충돌 정책이 필요함 |
| 하루에 여러 일기 허용 | 날짜 충돌을 피할 수 있음 | 하루에 하나의 일기라는 정책과 보관함·검색 구조까지 바뀜 |
| **초안을 보존하고 사용자가 선택한 날짜의 새 일기로 복구** | 기존 일기와 작성 내용을 함께 보호함 | 날짜에 다른 일기가 있으면 사용자가 다른 날짜를 선택해야 함 |

### 선택한 방법과 근거

원본 삭제를 화면에서 설명하고 `새 일기로 저장`을 제공합니다. 복구할 날짜에 이미 일기가 있으면 저장을 막고 날짜 변경을 안내합니다. 원래 날짜가 비어 있으면 그대로 복구할 수 있습니다. 자동 병합 정책은 추가하지 않았습니다.

- 초안의 제목·본문·감정·사진 문서를 그대로 사용합니다. 복구 날짜를 바꿔도 원래 수정 초안의 저장 키는 유지하므로 다른 신규 일기 초안을 건드리지 않습니다.
- 초안 UUID를 복구된 일기의 UUID로 사용해 같은 복구 요청을 반복해도 중복 일기를 만들지 않습니다.
- 완성본 생성과 초안 제거를 같은 저장 작업에 넣습니다. 최종 저장 실패 시 둘 다 되돌려 재시도할 수 있습니다.
- `sourceDeleted`, `dayConflict`, `storageFailure`, `emptyBody`를 구분해 사용자가 취할 행동에 맞는 안내를 제공합니다.

이 방식은 기존 하루 단위 정책과 저장 모델을 유지하면서 이미 저장된 고아 초안도 복구합니다. 저장 결과 API 전체를 `Result`로 바꾸는 리팩터링 대신, 이번 일기 저장 경로에 실패 원인 enum을 추가했습니다.

### 확인한 근거와 남는 범위

[JournalDraftRecoveryTests.swift](../WhisperTests/JournalDraftRecoveryTests.swift)에서 디스크 저장소 재개 후 글·사진 복원, 같은 날짜의 다른 일기 보존과 날짜 변경, 반복 복구, 최종 저장 실패 후 재시도를 확인했습니다. 구현은 [RecordStore.swift](../Whisper/RecordStore.swift)의 `saveJournalDraft`와 [JournalViews.swift](../Whisper/JournalViews.swift)의 삭제된 원본 안내·날짜 선택입니다.

같은 날짜의 두 일기를 합치는 기능은 구현하지 않았습니다. 이는 추가 충돌 정책이 필요한 후속 제품 선택입니다.

## #32 — 이전 버전 일기의 사진을 원본 변경 전에 보존

이슈: [#32](https://github.com/Youngmin322/whisper/issues/32) · 구현 커밋: `770775a`

### 왜 필요했는가

현재 문서 스냅샷을 가진 일기는 원본 순간을 삭제해도 사진을 유지합니다. 그러나 V6에서 넘어온 일기 중 `DiaryPage`가 없는 일기는 원본 순간의 사진을 가져와 보여줬습니다. 원본을 삭제하면 사진이 사라지고, 원본 사진을 바꾸면 과거 일기의 사진도 달라질 수 있었습니다.

영향은 독립 문서가 없는 이전 데이터에 한정됩니다. 그래도 업데이트한 사용자의 기록을 보호하는 문제이며, 새 일기와 이전 일기의 보존 동작이 달라 배포 전에 수정할 필요가 있었습니다.

### 선택지와 판단

| 선택지 | 장점 | 이번에 선택하지 않은 이유 |
|---|---|---|
| 사진도 함께 사라진다고 경고 | 구현 범위가 작음 | 이미 모아 둔 일기를 독립적으로 보존하는 현재 동작과 달라짐 |
| 연결된 원본 순간의 삭제 금지 | 삭제로 인한 손실 예방 | 원본 사진 수정은 보호하지 못하며 삭제 의도를 제한함 |
| 업데이트·첫 실행 때 모든 과거 일기의 문서 생성 | 전체 데이터를 일괄 정리 가능 | 시작 시 전체 기록의 읽기·쓰기가 필요하고, 실패 시 재개·완료 관리까지 추가해야 함 |
| 일기를 읽거나 다시 저장할 때 문서 생성 | 필요한 기록만 변환 | 한 번도 다시 열지 않은 일기는 원본 변경 전에 보호되지 않음 |
| **원본 수정·삭제 직전에 연결된 과거 일기의 문서 생성** | 사진이 사라질 수 있는 경계에서 보존 | 연결된 일기 수에 따라 해당 변경 작업의 저장량이 늘어날 수 있음 |

### 선택한 방법과 근거

원본 순간의 `update`와 `delete`가 값을 바꾸기 전에 `stageLegacyJournalSnapshots`를 실행합니다. 이미 유효한 독립 문서가 있는 일기는 건너뛰고, 없는 일기만 현재 원본 사진과 배치를 포함한 문서로 보존합니다.

- 사진 문서 생성과 원본 변경은 **같은 ModelContext의 한 번의 최종 저장**으로 처리합니다. 문서 생성이나 저장에 실패하면 원본 변경도 진행하지 않거나 되돌립니다.
- 기존 `DiaryPage`와 `DiaryDocument`를 재사용합니다. 과거 SwiftData 스키마의 모델을 수정하거나 새 사진 저장 시스템을 만들지 않았습니다.
- 과거의 별도 회고 필드는 문서를 읽고 편집 초안을 준비할 때 함께 반영해 회고가 빠지거나 두 번 붙지 않게 했습니다.

이 선택의 근거는 전체 기록을 미리 변환하지 않아도 사진이 없어지는 변경 경로를 막을 수 있다는 점입니다. 일괄 변환보다 성능이 좋다고 측정한 것은 아닙니다. 사진 전용 저장소와 참조 수 관리는 장기적으로 검토할 수 있지만 이번 보존 문제에는 변경 범위가 더 큽니다.

### 확인한 근거와 남는 범위

[LegacyJournalSnapshotTests.swift](../WhisperTests/LegacyJournalSnapshotTests.swift)는 실제 V6 디스크 저장소를 만들고 현재 버전으로 연 뒤 원본 수정·삭제를 각각 실행합니다. 재개 후 사진 데이터·위치·출처·설명·회고 유지와 삭제 저장 실패 시 원본 보존·재시도를 확인했습니다. 구현은 [RecordStore.swift](../Whisper/RecordStore.swift)의 `stageLegacyJournalSnapshots`입니다.

이미 이전 실행에서 사라진 사진 데이터까지 되살리는 방식은 아닙니다. 스냅샷이 없는 일기는 변경 직전의 원본을 보존하므로, 그보다 앞선 사진 상태를 복원할 수도 없습니다. 독립 보존을 위해 사진 데이터가 복제될 수 있다는 저장 공간 비용도 있습니다.

## #33 — 한 저장소로 빌드·테스트를 재현할 수 있게 구성

이슈: [#33](https://github.com/Youngmin322/whisper/issues/33) · 구현 커밋: `a179d16`

### 왜 필요했는가

Xcode 프로젝트는 저장소 밖의 `../WhisperCore`를 참조했습니다. 현재 컴퓨터에는 그 폴더가 있어 빌드할 수 있었지만, 앱 저장소만 복사한 환경에서는 의존성 해석이 실패했습니다. CI도 앱 저장소만 checkout하므로 패키지 준비 단계가 빠져 있었습니다.

개발자의 추가 폴더에 의존하면 다른 환경에서 같은 커밋을 검증하기 어렵습니다. 앱 테스트 대상의 최소 OS가 앱보다 높고, CI의 특정 시뮬레이터 이름과 브랜치 조건도 실제 검증 범위를 제한했습니다.

### 선택지와 판단

| 선택지 | 장점 | 이번에 선택하지 않은 이유 |
|---|---|---|
| 로컬·CI에서 두 저장소를 고정 리비전으로 checkout | 패키지의 독립 저장소 유지 | 경로·권한·리비전 조합을 두 저장소에서 관리해야 함 |
| 원격 SPM 패키지와 버전 고정 | 다른 앱에서 재사용하고 독립 배포하기 좋음 | 원격 접근·버전 발행·권한 구성이 추가로 필요함. 독립 배포가 이번 수정의 요구사항은 아님 |
| Git submodule 사용 | 외부 코드의 정확한 리비전 고정 | 재귀 checkout과 하위 모듈 업데이트 절차가 추가됨 |
| 패키지 소스를 앱 타깃에 직접 합치기 | 한 저장소로 빌드 가능 | 기존 모듈 경계·import·리소스 접근에 불필요한 변경 발생 |
| **기존 패키지를 저장소 내부 로컬 패키지로 포함** | 앱 커밋에 패키지 코드가 함께 고정되고 한 번의 checkout으로 준비됨 | 외부 형제 패키지와 별도로 변경할 경우 동기화 방침이 필요함 |

### 선택한 방법과 근거

`Packages/WhisperCore`에 기존 패키지를 포함하고 프로젝트의 참조 경로를 바꿨습니다. `WhisperCore`·`WhisperDesignSystem` 모듈과 패키지 리소스 구조는 유지했습니다. 앱의 기록 기능을 수정하면서 패키지 배포 체계까지 새로 만드는 부담을 피하고, 한 저장소만으로 검증할 수 있게 한 선택입니다.

또한 테스트 대상의 최소 OS를 앱과 같은 iOS 26.0으로 맞추고, 설치된 iOS 26 이상 iPhone 시뮬레이터를 찾는 공통 스크립트를 로컬·CI에서 사용하도록 했습니다. 특정 기기에서 확인하려면 환경 변수로 ID를 지정할 수 있습니다. CI push 대상에는 `dev`를 추가했습니다.

### 확인한 근거와 남는 범위

`git archive`로 커밋된 파일만 추출하고 외부 형제 패키지가 없는 체크아웃에서 iOS 26.5의 전체 151개 테스트와 서명 없는 기기용 Release 아카이브 생성에 성공했습니다. 의존성·리소스가 현재 컴퓨터의 형제 폴더 없이 준비됨을 확인한 결과입니다.

구현 근거: [프로젝트 설정](../Whisper.xcodeproj/project.pbxproj), [패키지](../Packages/WhisperCore/Package.swift), [테스트 스크립트](../Scripts/test-ios.sh), [CI](../.github/workflows/ios-ci.yml), [환경·명령 안내](../README.md).

이번 작업에서 push하지 않았으므로 GitHub Actions의 실제 원격 실행 성공까지 확인한 것은 아닙니다. iOS 26.0은 설치된 런타임이 없어 실행하지 못했습니다. 배포용 서명·업로드도 별도입니다. 다른 프로젝트가 형제 패키지를 계속 사용한다면 향후 변경을 어느 저장소에서 관리하고 동기화할지 정해야 합니다.

## #34 — 기존 순간 수정에도 독립 초안 자동 저장 적용

이슈: [#34](https://github.com/Youngmin322/whisper/issues/34) · 구현 커밋: `ca18362`

### 왜 필요했는가

새 순간과 일기는 초안을 보관했지만, 기존 순간의 수정은 화면의 `@State`에만 남았습니다. 저장 전에 뒤로 이동하거나 앱이 종료되면 본문·감정·사진 변경을 복구할 수 없었습니다. 같은 앱의 작성 화면마다 이탈 동작이 다른 상태였습니다.

짧은 기록을 자주 쓰고 수정하는 앱에서 작성 내용 보호는 반복적으로 사용하는 기본 동작입니다. 수정 내용을 원본과 구분해서 보관하면 실수로 닫았을 때 복구하면서도 저장 전 원본을 유지할 수 있습니다.

### 선택지와 판단

| 선택지 | 장점 | 이번에 선택하지 않은 이유 |
|---|---|---|
| 나갈 때만 저장·버리기 확인 | 일반적인 이탈을 보호하며 구현이 작음 | 앱 종료·프로세스 중단 후 복구하지 못하고 자주 쓰는 흐름을 끊음 |
| 수정 중 뒤로 가기·닫기 제한 | 일부 우발적 이탈 예방 | 이동을 제한하며 앱 종료에 대비하지 못함 |
| 변경할 때 원본에 바로 자동 저장 | 별도 초안 없이 최신 내용 저장 | 작성 중 내용이 완성본을 바꾸고, 수정 취소 시 이전 원본을 유지하기 어려움 |
| 새 순간의 단일 초안 공간을 재사용 | 저장 구조 변경이 작음 | 새 순간과 여러 기존 순간의 수정이 서로 덮어쓸 수 있음 |
| 새 수정 초안 테이블·범용 편집 프레임워크 도입 | 향후 기능을 확장하기 좋음 | 기존 초안 저장 구조로 해결 가능한 문제에 스키마·상태 구조 변경이 늘어남 |
| **기존 초안 저장소에 순간 ID별 수정 초안 추가** | 원본을 유지하면서 재개 가능하고 작성 화면 간 정책을 맞춤 | 변경마다 저장하는 기존 방식의 비용은 별도 측정이 필요함 |

### 선택한 방법과 근거

`moment:edit:<원본 ID>` 키로 수정 초안을 분리했습니다. 새 순간의 `moment` 초안과 다른 순간의 수정 초안을 함께 보관할 수 있습니다. `RecordDraft`에 선택 필드 `existingRecordID`를 추가했고, 기존 JSON에 그 필드가 없어도 복원되게 했습니다. SwiftData의 새 모델·스키마는 추가하지 않았습니다.

- 변경·화면 이탈·비활성화 시 초안을 보관하고 홈에서 재개합니다. 수정 모드 진입만으로는 초안을 만들지 않습니다.
- `닫기`는 초안을 유지합니다. `초안 버리기`는 확인 후 초안만 지우고 원본을 보존합니다. 명시적인 닫기의 저장이 실패하면 화면에 남아 재시도하도록 합니다.
- 최종 수정 저장 전까지 원본은 그대로입니다. 원본 갱신과 초안 제거를 같은 저장 작업에 넣어 최종 실패 시 함께 되돌립니다.
- 원본 순간이 삭제된 수정 초안은 설명 후 오늘의 새 순간으로 복구합니다. 이때 다른 신규 초안은 유지합니다.

이 방식은 기존 `WritingDraftStore`의 저장·재시도·완료 처리와 공유 ModelContext를 활용합니다. 편집 프레임워크를 새로 도입하기보다 기존 경계를 확장해 데이터 보호를 완성하는 것이 배포 전 변경 범위에 적합했습니다.

### 확인한 근거와 남는 범위

[MomentEditDraftTests.swift](../WhisperTests/MomentEditDraftTests.swift)에서 여러 수정 초안과 신규 초안의 분리, 디스크 재개, 원본 보존, 최종 실패 시 되돌림, 임시 저장 실패 후 재시도, 원본 삭제 복구, 이전 JSON 호환을 확인했습니다. [WritingDraftViewTests.swift](../WhisperTests/WritingDraftViewTests.swift)에서는 실제 편집 뷰의 본문 변경·닫기·재개를 검증했습니다. iPhone SE 시뮬레이터에서도 키보드로 수정한 뒤 닫기·재개·저장 흐름을 확인했습니다.

구현: [RecordDraft.swift](../Whisper/RecordDraft.swift), [WritingDraftStore.swift](../Whisper/WritingDraftStore.swift), [RecordDetailView.swift](../Whisper/RecordDetailView.swift), [RecordStore.swift](../Whisper/RecordStore.swift).

디스크 저장 자체가 실패하는 동안에는 최신 내용을 메모리에 유지해 재시도합니다. 그 상태에서 앱 프로세스까지 종료되면 아직 저장하지 못한 내용을 보장할 수 없습니다. 저장 빈도 조절은 측정 후 검토하며, 도입하더라도 닫기·비활성화 때 마지막 변경을 저장하는 처리는 필요합니다.

## #36 — 흰 글자용 배경색으로 주요 조작의 대비 개선

이슈: [#36](https://github.com/Youngmin322/whisper/issues/36) · 구현 커밋: `da68d20`

### 왜 필요했는가

홈의 `+ 순간 남기기`는 14pt medium 흰색 글자와 `#F4523B` 배경을 사용했습니다. sRGB 상대 휘도로 계산한 대비는 약 **3.43:1**이었습니다. 일반 텍스트의 가독성을 평가하는 참고 기준인 **4.5:1**보다 낮아 작은 버튼 글자를 읽기 어렵게 할 수 있었습니다. 누를 때 버튼 전체의 투명도를 낮추는 방식도 대비를 약하게 만들 수 있었습니다.

여기서는 [W3C WCAG 2.2의 대비 설명](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)을 색 조합의 판단 기준으로 참고했습니다. 네이티브 앱 전체의 접근성 적합성이나 App Store 심사 결과를 판단한 것은 아닙니다.

### 선택지와 판단

| 선택지 | 장점 | 이번에 선택하지 않은 이유 |
|---|---|---|
| 앱 전체 강조색을 더 짙게 변경 | 같은 색을 쓰는 곳을 한 번에 바꿈 | 불꽃·장식 등 읽기 문제가 없는 표현도 함께 바뀜 |
| 밝은 배경에 어두운 글자 사용 | 충분한 대비를 갖는 다른 조합 가능 | 흰 글자를 사용하는 기존 주요 컨트롤 표현이 달라짐 |
| 버튼 글자를 크게·굵게 만들기 | 글자 식별을 도울 수 있음 | 작은 홈 버튼의 배치가 바뀌며, 글꼴 조정만으로 충분한 대비를 확보했다고 볼 수 없음 |
| **흰 글자용 배경 토큰과 더 짙은 누름 상태 추가** | 영향을 필요한 컨트롤에 한정하고 상태별 대비 확보 | 전체 토큰의 소유 위치 통합은 별도 작업으로 남음 |

### 선택한 방법과 근거

기존 강조 글자색과 같은 `#B64F35`를 흰 글자용 컨트롤 배경으로 사용했습니다. 기본 상태는 **5.05:1**, 누른 상태의 `#983F2A`는 **6.82:1**입니다. 누름 표현은 버튼 전체 투명도를 낮추는 대신 배경색을 더 짙게 바꾸었습니다.

홈·공통 주요 버튼·활성 필터·안내 숫자에 적용하고, 불꽃 등 기존 장식의 강조색은 유지했습니다. 색상의 역할을 토큰 이름으로 구분하므로 새 컨트롤에서도 읽기용 배경을 선택하기 쉽습니다. 특정 화면의 색만 하드코딩하는 수정보다 재사용 범위를 분명히 하는 선택입니다.

### 확인한 근거와 남는 범위

색상 상수에서 W3C의 sRGB 상대 휘도와 대비 공식을 적용해 위 비율을 다시 계산했습니다. 구현은 [Color+Whisper.swift](../Whisper/Color+Whisper.swift), [WhisperButtonStyle.swift](../Whisper/DesignSystem/WhisperButtonStyle.swift), [FlameHomeScreen.swift](../Whisper/FlameHomeScreen.swift) 등입니다. 변경 후 전체 테스트와 시뮬레이터의 주요 조작 흐름이 통과했습니다.

이 비율은 명시한 전경·배경 색 조합에 대한 계산 결과입니다. 저시력 사용자의 실제 읽기 평가를 수행한 것은 아니며, VoiceOver·최대 글자 크기·모든 화면의 접근성 검증을 대신하지 않습니다.

## 이번 구현에서 사용한 구조적 원칙

| 원칙 | 적용 | 이 프로젝트에서 선택한 이유 |
|---|---|---|
| 원본과 편집 초안 분리 | 순간별 수정 초안을 별도로 보관 | 완성본을 유지하면서 이어 쓰기·초안 버리기를 구현하기 위함 |
| 문서 스냅샷 | 원본 변경 전 과거 일기의 사진 문서 생성 | 과거 일기가 원본의 수명과 수정에 의존하지 않게 하기 위함 |
| 같은 저장 경계에서 함께 확정 | 원본 변경+스냅샷, 완성본 저장+초안 제거 | 절반만 저장되는 상태를 피하고 실패 시 함께 되돌리기 위함 |
| 반복 요청의 동일 결과 | 복구에 초안 UUID 사용 | 재시도 시 중복 기록 생성을 피하기 위함 |
| 도메인 실패 원인 구분 | 일기 저장 실패 enum | 단순 재시도와 날짜 선택·새 일기 복구를 구별하기 위함 |
| 역할을 나타내는 디자인 토큰 | 흰 글자용 배경·누름 배경 | 장식용 강조색과 컨트롤 가독성을 별도로 관리하기 위함 |
| 기존 모듈 경계 유지 | 저장소 안의 로컬 Swift package | 재현 가능한 빌드를 만들면서 소스·리소스 사용 방식의 변경을 줄이기 위함 |

공유 ModelContext에서 관련 변경을 한 번에 확정하는 기존 구성을 활용했습니다. 별도의 Unit of Work 추상화, 공통 EditorSession, 전체 Repository 분리나 TCA 같은 프레임워크를 새로 도입한 것은 아닙니다. 이번 수정의 실패 경로를 테스트로 고정한 뒤, 해당 경계를 점진적으로 분리하는 편이 후속 리팩터링을 검증하기 쉽습니다.
